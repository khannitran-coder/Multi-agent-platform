# Context preparation workbench

Project source versions can now be selected explicitly for a canonical BA context preparation. The existing notes endpoint accepts an optional name (default Discovery notes). Source versions remain immutable, with project-wide monotonically increasing version numbers; these are not per-document revision chains. Selecting multiple versions intentionally includes both. There is no PDF extraction, upload parser, semantic policy verification or live model.

`POST /api/projects/{pid}/context-preparations` accepts the strict `ContextInput` contract: 1–20 distinct project source IDs, internal/client mode, method/audience, declared PM/internal/client approver, contract type, optional selected SOW and process references, and synthetic-only acknowledgement. Extra fields such as reviews, arbitrary context and authority evidence are rejected. All selected sources are checked against membership/project ownership. Context sources are built server-side from stored ID/version/hash/text. Principals are explicitly unverified prototype declarations; reviews is always empty. Data authorization in this candidate represents only the synthetic declaration and is never used as runtime authority.

The server releases the SQLite transaction before a bounded 10-second subprocess calls the pinned upstream schema validator and `domain.preflight`. It verifies the immutable dependency first and uses the existing BA interpreter, no model/CLI live flags. It persists the candidate context, form, deterministic context SHA-256, agent commit, findings and timestamp in additive `context_preparations`. A project audit event links the snapshot ID. GET of the same endpoint returns immutable history under the same membership check. Failed runtime/integrity checks return 503 and store no passing snapshot.

Schema and preflight findings are returned separately. Upstream preflight short-circuits on schema failures; after fixing these, additional domain/data findings can appear on the next check. A technical pass only means upstream schema and structural preflight accept the candidate. It does not verify that the chosen SOW is a contract, process references resolve to meaningful clauses, named people have authority, or the data is actually synthetic.

Every preparation has execution=blocked, business=pending, approval=not_approved. There is no execute endpoint for preparation IDs; the existing RunInput rejects context_id. Existing harness invocation still uses only its fixed công nợ fixture. Existing mock workflows continue to bind the latest source under their documented template behavior, not these context snapshots. Review of an existing artifact does not alter preparations or trusted reviews.

The UI saves each check independently, labels saved results apart from the editable form, supports selecting historical results and reusing a saved form, and remains usable on mobile. Sources can be added but never updated/deleted through this workbench. Large histories are currently returned in full; pagination and per-document version chains are deferred.
